읽은 날: 2026-11-14. 기준 커밋은 `e633ece`이다. 비교한 코드:

#### 3.4.1 부서 → 선택 입력 — **P0** 🔶 BE

시안: 라벨이 **`부서 (선택)`** 으로 바뀌었다(데스크톱·모바일 모두). 주석(`336:7011`) 원문: *"부서(워딩 수정할 수도) 정보는 선택 입력으로 변경"*. placeholder `부서를 입력하세요`는 그대로다.

| 항목 | 현재 | 바꿀 것 |
|---|---|---|
| 라벨 | `부서 (비공개)` (`mentor-fields.tsx:161`) | `부서 (선택)` |
| 검사 | `z.string().trim().min(1, "부서를 입력해 주세요.").max(128)` (`mentor-form.ts:22` `workShape`) | `z.string().trim().max(128)` — 빈 값 허용 |
| 다음 버튼 | 부서가 비면 비활성 | 이름·닉네임·회사·직무만 보고 켠다 |
| `hasBasics` | `draft.department`가 있어야 통과(`mentor-signup-draft.ts:74`) | 조건에서 뺀다. 안 빼면 추가 정보 새로고침 때 기본 정보로 잘못 튕긴다 |
| 정보 수정 | `mentorEditSchema`가 같은 `workShape`를 씀 | 함께 선택이 된다(의도한 결과) |
| 마이페이지 | `ProfileRow label="부서" value={profile.department}` (`me.tsx:323`) | 빈 값이면 `—` |

- **`(비공개)` 표시가 라벨에서 사라진다.** 부서가 다른 회원에게 보이지 않는다는 사실(명세 `department` 설명: *"비공개 (다른 회원에게 보이지 않음)"*)은 그대로다. 마이페이지 비공개 정보 카드에 이미 있다. 🔶 D3-4에서 "`부서 (선택·비공개)`처럼 둘 다 적을지" 디자이너에게 묻는다. 답 전에는 시안대로 `부서 (선택)`.
- 주석의 "워딩 수정할 수도"는 라벨 문구가 더 바뀔 수 있다는 뜻이다. 라벨은 한 곳(`MentorWorkFields`)에만 둔다.
- 🔶 **D3-1 (BE, 이슈 [#43](https://github.com/gsainfoteam/cheers-fe/issues/43)): 명세상 `department`가 필수다.** `GraduatedInfoRequestDto.required = ["department", "job", "contact"]`. `minLength`는 없어서 `""`가 통과할 수도 있다. BE에 물은 것:
  - 부서를 비울 때 **키 생략 / `null` / `""`** 중 무엇을 보내는가
  - `GraduatedProfileDto.department`(지금 `string`, nullable 아님)는 비었을 때 무엇으로 오는가
- ✅ **결정 (2026-11-14): BE 답을 기다리지 않고 `""`를 보내는 임시 구현으로 진행한다**(키가 필수이므로 생략할 수 없다). 보내는 자리에 `// 임시: 이슈 #43 — 빈 부서는 ""` 주석을 남긴다. 스테이징에서 `""` 저장이 400이면 #43에 남기고 BE 우선 처리를 요청한다. 답이 오면 정한 표현(생략·`null`)으로 바꾸고 주석을 걷는다.
- ✅ **명세 반영 (2026-11-14, `bun run api:sync`):** `department`가 요청 `required`에서 빠졌고 *"선택 입력, 안 보내거나 빈 값이면 null 로 저장"*. 응답 `GraduatedProfileDto.department`는 *"선택 입력이라 없으면 null"*(nullable). FE는 **비었으면 키를 보내지 않는다**(`lib/profile-form.ts` `departmentRequestOf`, 가입·정보 수정 공용). 응답의 null은 폼에서 `""`, 마이페이지에서 `등록하지 않음`으로 읽는다. `""`를 보내던 임시 구현과 주석은 걷어냈다. 이슈 #43은 정리 댓글과 함께 닫았다(2026-11-14).

#### 3.4.2 닉네임 중복을 `다음`에서 확인 — P1 🔶 BE

`960:10010`(사용 중인 경우) 주석 원문: *"다음 버튼 눌렀을 때 중복 확인"*. 문구 `이미 사용 중인 닉네임이에요.`(칸 Error)는 코드와 같다(`mentor-form.ts:56`).

지금은 확인 API가 없다(선배 가이드 §7 #3). 중복은 **추가 정보의 `가입 완료`** 에서 409로 알게 되고, 기본 정보로 되돌아가 칸에 문구를 띄운다(`extra.tsx:113-119`). 시안은 한 화면 앞인 `다음`에서 알려 주길 원한다.

- 🔶 **D3-2 (BE, 이슈 [#43](https://github.com/gsainfoteam/cheers-fe/issues/43)): 닉네임 사용 가능 여부 확인 API**(예: `GET /user/graduated/nickname/availability?nickname=`)를 요청했다. `GET /cheers`의 `nickname` 쿼리는 부분 일치 검색이라 대신 쓸 수 없다.
- ✅ **결정 (2026-11-14): API가 생길 때까지 지금 흐름(가입 완료 때 409 → 기본 정보로 되돌림)으로 구현한다.** 이번 작업에서 이 부분은 코드 변경이 없다.
- ✅ **명세 반영·구현 (2026-11-14):** `GET /api/v1/user/graduated/nickname/check?nickname=` → `{ available: boolean }`. 대소문자 구분 없이 이미 쓰는 이름이면 false, **조회만 하고 예약하지 않는다**, 가입 중(`next_step=profile`)이 아니면 403. 아래 "API가 생기면"대로 연결했다(`profile.tsx`). 확인 요청이 실패하면 막지 않고 넘긴다 — 가입 완료의 409 되돌림이 그대로 남아 있다.

#### 3.5.3 커피챗 참여 설정 — **P0**

**선배 가이드 §2.7의 구조가 바뀌었다.**

| | 이전 시안 (지금 코드) | 새 시안 |
|---|---|---|
| 묶음 | `공유할 연락처`(이메일, 필수) + 구분선 + `신청 알림`(휴대폰) | **`커피챗 참여 설정 (선택)`** 한 묶음 |
| 뜻 | 이메일 = 학생에게 공유, 휴대폰 = 알림만(공유 안 함) | 둘 다 **"커피챗 알림을 받을 연락처"** |
| 컨트롤 | 칸 두 개 | **체크박스 2개(`카카오 알림톡`, `이메일`) + 채널별 입력 칸** |
| 둘 다 안 받기 | 고를 자리 없음 | **둘 다 체크 해제** = 커피챗 미참여 |

문구:
- 제목: `커피챗 참여 설정 (선택)`(Label/Medium `text-ink`). 레이어 이름은 `연락 설정 (선택)`이다.
- 설명: `커피챗 알림을 받을 연락처를 입력해주세요. 입력하지 않으면 커피챗에 참여할 수 없어요.`(Body/Small `text-ink-soft`). 모바일은 `입력해주세요.` 뒤에서 줄바꿈.
- 선택지 순서: **`카카오 알림톡` · `이메일`**. 학생과 달리 **`알림 받지 않기`가 없다.**
- 칸 placeholder: `전화번호를 입력해주세요.` / `이메일을 입력해주세요.`. 라벨·도움말 없음.
- 입력 예시: `010-1234-5678`(하이픈 표시), `email@naver.com`.

모양:
- 제목 → 설명 → 선택지 사이 모두 8. 선택지 줄 사이 8.
- 체크박스는 `Cheers / Checkbox`(44 높이, 상자 22, 글자 사이 12, Body/Small). `CheckRow`(`h-12` = 48)에 44 변형을 더한다(2장 2.6.3과 같은 작업).
- 데스크톱: 체크박스 140 + 칸(`flex-1`, 52 높이, `border-control`) 한 줄.
- 모바일: 체크박스 줄(폭 전체) 아래에 칸, 간격 8.

동작(시안 주석 원문):
- 카카오 알림톡 체크박스(`I1159:10123;332:6145`): *"진입 시 기본적으로 check 되어있게, 커피챗 참여 안 하려면 둘 다 check를 해제 해야 하도록하여서 커피챗 참여 유도(?)"*
- `가입 완료`(`346:9642`): *"check 된 연락처를 입력 완료 해야 가입 완료 버튼이 활성화"*

정리하면:
1. **처음에는 두 채널 모두 체크되어 있다.** 학생(셋 다 꺼짐)과 반대다.
2. 체크한 채널은 칸이 비었거나 형식이 틀리면 `가입 완료`를 막는다.
3. **둘 다 해제하면 칸을 채우지 않아도 `가입 완료`가 켜진다.** 이 선배는 "희망하지 않음"이 된다.
4. 체크를 해제한 채널의 칸 모양은 시안에 없다(🔶 D3-5). 그 전에는 **2장 2.6.3과 같이 칸을 감춘다.** 값은 폼 state에 남겨 두어 다시 체크하면 되살아난다.

**서버 매핑 — 지금 명세로 끝난다.** 선배는 둘 다 false가 이미 허용된다. `CheersCardDto.can_request`(*"연락 설정이 \"희망하지 않음\"이면 false"*)와 공유 409(*"내 연락 설정이 희망하지 않음이라 공유할 연락처가 없음"*)가 그 상태를 다룬다. 학생 D2-2 같은 막힘이 없다.

```ts
contact: {
  kakao_enabled: values.kakao,
  email_enabled: values.email,
  // 끈 채널의 값은 보내지 않는다 — 알림에도 공유에도 쓰지 않을 개인정보를 남기지 않는다
  phone: values.kakao ? digitsOf(values.phone) : null,
  email: values.email ? values.emailAddress.trim() : null,
}
```

- 빈 문자열은 400이다(`ContactRequestDto`: *"값이 없으면 null 또는 생략 (\"\" 는 400)"*). 위 매핑은 켠 채널에서 빈 값을 보낼 수 없다(검사가 막는다).
- 끈 채널에 `null`을 보내면 저장된 값이 지워진다. 정보 수정에서 잠깐 끄고 저장하면 번호를 다시 쳐야 한다. 이 결과가 괜찮은지 D3-5에 함께 묻는다.

**공유 규칙 (D3-3 결정, 2026-11-14)**
- 이 칸에 입력한 연락처는 **알림용이자 공유용**이다. 공유용 연락처를 따로 받지 않는다.
- 선배가 `내 연락처 공유`를 누르면 **입력한 연락처가 모두** 학생에게 간다. 이름과 함께 이메일, 휴대폰 번호가 간다.
- "입력한 연락처"는 **체크한 채널의 값**이다. 위 매핑에서 끈 채널은 `null`로 저장되므로 공유되지 않는다. 예를 들어 카카오만 켠 선배는 이름과 휴대폰 번호만 공유된다.
- 이 규칙 때문에 끈 채널의 값을 `null`로 보내는 매핑이 더 중요해진다. D3-5에서 "끈 채널의 값도 저장해 둔다"로 바뀌면, 그 값이 공유에 실리지 않도록 BE가 `*_enabled`를 함께 봐야 한다. 그 경우 BE와 다시 맞춘다.
- **선배 가이드 §2.7의 디자인 의도("휴대폰은 절대 공유되지 않는다")는 이 결정으로 뒤집혔다.** 그 문장을 근거로 쓴 화면 문구를 모두 고친다(3.6).

**공유 안내 문구 (시안 없음, 임시)**
- 휴대폰 번호가 학생에게 전달된다는 사실을 선배가 입력하는 자리에서 알아야 한다. 새 시안의 설명은 "알림을 받을 연락처"라고만 말한다.
- 설명 아래에 Body/Small `text-ink-soft` 한 줄을 임시로 둔다: `연락처를 공유한 학생에게는 입력한 연락처가 이름과 함께 전달돼요.`(3.9)
- 🔶 D3-9로 디자이너에게 문구와 자리를 확인받는다. 시안에 없는 줄이므로 "시안과 다르게 둔 것"에 기록한다.

### 3.6 마이페이지·정보 수정·연락처 공유에 번지는 영향 — P0·P1 (BE 동작 확인)

`me_/edit.tsx`는 가입과 **같은 칸 묶음**(`MentorWorkFields`, `MentorExtraFields`, `MentorContactFields id="contact"`)과 같은 스키마(`mentorEditSchema`)를 쓴다(`:188-240`). 3.4.1과 3.5.3이 그대로 따라간다.

- **정보 수정:** 부서가 선택이 되고, 연락처 묶음이 `ContactChannelFields`로 바뀐다. `id="contact"` 닻(마이페이지 `연락처·알림 번호 수정` 링크가 오는 자리)은 새 묶음 바깥에 그대로 둔다. 화면 문구·배치는 선배 마이페이지 섹션 장에서 시안과 맞춘다. 이 장에서는 **깨지지 않게만** 한다.
- **마이페이지 `ContactCard`(`me.tsx:334-380`):** `공유할 연락처` / `신청 알림` 두 칸 구조가 새 모델과 맞지 않는다. 이 장에서는 최소한으로 고친다.
  - 켠 채널의 값만 보인다. 이메일은 `email_enabled`일 때만, 휴대폰은 지금처럼 `kakao_enabled`일 때만 보인다(지금 이메일은 켜짐과 무관하게 `contact.email`을 보인다).
  - `알림 번호는 학생에게 공유되지 않아요.`(`me.tsx:367`)는 **D3-3 결정과 반대이므로 지운다.** 그 자리에 3.5.3과 같은 임시 안내를 둔다.
  - 둘 다 꺼짐이면 `커피챗 알림을 받지 않아요.` 한 줄(임시 문구, 시안 없음)
  - 카드 제목·구조 개편은 마이페이지 섹션 장에서 한다.
- **연락처 공유 — D3-3 결정에 맞춘다.** 지금 화면은 "이름·이메일만 보낸다, 알림톡 번호는 공유되지 않는다"고 말한다. 3.5.3이 들어가면 휴대폰도 공유되므로 **이 장에서 같이 고친다.** 그대로 두면 선배에게 사실과 다른 안내를 하게 된다.
  - `lib/mentor-contact.ts`: `myContactEmailOf`를 **`mySharedContactOf(me): { email: string | null; phone: string | null }`** 로 바꾼다. 켠 채널의 값만 돌려준다(`email_enabled ? email : null`, `kakao_enabled ? phone : null`). 공유 확인과 받은 신청 상세가 **같은 값**을 보여야 한다는 원래 규칙은 그대로다.
  - 공유 확인(`share.tsx:82-100`):
    - 정의 행: `이름` + `이메일`(있을 때) + `휴대폰`(있을 때, `formatPhone`). 값이 없는 행은 `—`로 두지 않고 **줄을 뺀다.** 학생에게 가지 않는 값을 목록에 둘 이유가 없다.
    - `알림톡 수신 번호는 공유되지 않아요.` 삭제
    - 버튼 `이름·이메일 공유` → **`연락처 공유`**(무엇이 가는지는 위 목록이 말한다)
    - `⚠️ 이슈 #26` 주석 삭제
  - 받은 신청 상세 `ContactMethods`(`applications/$applicationId.tsx:250-330`):
    - `내 연락처 공유` 카드 설명 `이름과 이메일을 보내 학생이 연락할 수 있게 해요.` → `이름과 연락처를 보내 학생이 연락할 수 있게 해요.`(임시, D3-9와 함께 확인)
    - 카드 값: 이메일 하나 → 공유될 연락처(이메일, 휴대폰)를 줄로
    - 막는 조건: 지금은 **이메일이 없으면** `공유할 이메일이 없어요. 마이페이지에서 등록해 주세요.`로 막는다(`:319-321`). 카카오만 켠 선배도 휴대폰을 공유할 수 있으므로 **둘 다 없을 때만** 막고, 문구를 `공유할 연락처가 없어요. 마이페이지에서 등록해 주세요.`로 바꾼다. 서버 409(*"희망하지 않음이라 공유할 연락처가 없음"*)와 같은 조건이다.
  - 학생 쪽 보낸 신청 상세(`shared_contact`의 이메일·휴대폰, `:444-462`)는 이미 둘 다 보여 준다. 바꿀 것 없다.
  - **BE 동작 확인:** 명세의 `ShareContactResponseDto`에는 이미 `shared_email`·`shared_phone`이 있다. 결정을 BE에 전달하고, 스테이징에서 아래를 확인한다.
    - 두 채널 켠 선배가 공유 → 응답에 이메일·휴대폰 둘 다
    - 카카오만 켠 선배 → `shared_phone`만, 409가 나지 않음
    - 이메일만 켠 선배 → `shared_email`만
    - 다르게 동작하면 BE 수정 요청(이 결정이 기준이다)
  - 공유 확인·상세의 화면 모양 자체는 받은 신청·연락처 공유 섹션 장에서 시안과 다시 맞춘다. 이 장에서는 **사실과 다른 문구를 없애고 휴대폰을 함께 보여 주는 것까지** 한다.
- **선배 둘러보기:** 둘 다 끈 선배는 `can_request=false`가 된다. 목록 카드의 신청 버튼 처리는 이미 `can_request`를 따른다(학생 줄기). 이 장에서 바꿀 것 없다. 다만 지금까지는 #26 임시 결정 때문에 `false`가 나올 수 없었으므로, **처음으로 실제로 생기는 상태**다. 스테이징에서 한 번 확인한다.

### 3.9 구현하며 계획과 다르게 한 것 (2026-11-14)

- **`ContactChannelFields`에 `optOut`을 아직 두지 않았다.** 지금 쓰는 곳이 선배뿐이라 쓰지 않는 분기를 미리 만들지 않았다. 검사 규칙도 `requireOne` 옵션 없이 "켠 채널만 검사, 둘 다 끔 허용"인 선배 규칙 하나다. 학생(2장 2.6.3)을 구현할 때 `알림 받지 않기` 선택지와 "하나 이상 선택" 규칙을 이 두 파일에 더한다.
- **검사 규칙을 `contact-channel-form.ts`로 분리했다.** 컴포넌트 파일에서 스키마를 내보내면 lint(`react-refresh/only-export-components`)에 걸린다.
- **선배 문구는 `MentorContactFields`가 계속 갖는다.** 가입 추가 정보와 정보 수정이 같은 제목·설명·안내를 쓰므로, 그 래퍼가 `ContactChannelFields`에 선배 문구를 넣어 준다.
- **임시 공유 안내 문구를 바꿨다.** 계획의 `연락처 공유를 수락한 학생에게…`는 흐름과 맞지 않는다(공유는 선배가 하고 학생은 수락하지 않는다). `연락처를 공유한 학생에게는 입력한 연락처가 이름과 함께 전달돼요.`로 했고, `SHARED_CONTACT_NOTICE` 하나로 추가 정보·정보 수정·마이페이지가 같이 쓴다(D3-9).
- **마이페이지 연락처 카드는 "둘 다 꺼짐" 한 줄 대신 채널마다 꺼짐을 적는다** — `이메일 알림을 받지 않아요.` / `카카오 알림톡을 받지 않아요.` 지금 카드가 두 칸 구조라 칸마다 비는 이유를 적는 쪽이 자연스럽다. 카드 개편은 마이페이지 섹션에서 한다.
- **빈 부서 표기는 `—`가 아니라 `등록하지 않음`이다.** 같은 카드의 다른 빈 값(프로필 링크 등)이 이미 `등록하지 않음`을 쓴다.
- **단계 막대 고정의 위아래 여백은 `py-2` + `-my-2`로 상쇄했다.** 고정되기 전에는 시안 간격(28)이 그대로이고, 고정되면 막대 위아래에 바탕 8이 생긴다. 393에서 눈으로 확인이 남았다.
- **받은 신청 상세의 `내 연락처 공유` 카드 값은 줄바꿈으로 이메일·휴대폰을 나눈다**(`whitespace-pre-line`). 학생 쪽 `학생에게 직접 연락` 카드는 한 줄이라 영향 없다.
