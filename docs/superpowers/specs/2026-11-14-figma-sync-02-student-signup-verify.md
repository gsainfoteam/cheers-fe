### 2.2 약관 동의 (`334:6123` / `334:6011`, 완료 `334:6365` / `334:6235`): 일치 ✅

- **문구:** `약관 동의` / `서비스 이용에 필요한 약관을 확인해 주세요.` / `전체 동의` / `[필수] 서비스 이용약관` / `[필수] 개인정보 수집·이용 동의` / `동의하고 다음`

- **완료 상태:** 체크박스 `bg-ink-fill`·`border-ink`·흰 체크, 버튼 Disabled → Primary. 코드는 필수 항목이 모두 체크되면 버튼을 켠다(`terms.tsx:74-77`). 지금은 두 항목이 모두 필수라 결과가 같다.

#### 2.3.2 칸을 떠날 때 도메인 검사 — P1 (D2-4 결정)

도메인 오류 상태에서 **버튼이 Disabled다.** 서버의 400으로 오류를 띄우려면 버튼을 먼저 눌러야 하므로, 이 상태는 **제출 전에 클라이언트에서 검사한다**는 뜻이다.

✅ **D2-4 (2026-11-14):** 오류는 **칸을 떠날 때(blur)** 검사해서 띄운다. 도메인이 틀린 동안 버튼은 Disabled다. **허용 도메인은 `gist.ac.kr`** 이다.

- **검사 규칙:**
  - 값을 `trim().toLowerCase()`한 뒤 `@` 뒤의 도메인이 `gist.ac.kr`이거나 `.gist.ac.kr`로 끝나는지 본다. 학생 메일 `@gm.gist.ac.kr`도 통과한다.
  - 정규식: `/^[^\s@+]+@([a-z0-9-]+\.)*gist\.ac\.kr$/`
  - 하위 도메인까지 받는 이유: 시안 placeholder와 예시가 `@gm.gist.ac.kr`이다. 서버의 허용 도메인 목록은 superadmin이 바꾸는 값이다(`PUT /manager/v1/school/{schoolPk}/email-domain`). 클라이언트 검사는 **너무 막지 않는 쪽**으로 두고, 최종 판단은 서버 400에 맡긴다.
- **시점:**
  - 처음 칸을 떠난 뒤부터 오류를 보여 준다. 그 뒤로는 값이 바뀔 때마다 다시 검사한다. 고치는 즉시 오류가 사라지고 버튼이 켜진다.
  - 버튼 Disabled 조건 = 값이 비었음 || 도메인 검사 실패 || 보내는 중 || 409 표시 중(2.3.3)
  - 칸을 떠나기 전에도 도메인이 틀리면 버튼은 꺼 둔다. 오류 문구만 blur 뒤에 보인다.
- **문구:** 시안 `gm 메일을 입력해주세요.`. 서버 400 매핑(`:303-305`)도 같은 문구로 바꿔 예비용으로 둔다.
  - 허용 도메인이 `gist.ac.kr` 전체라서 "gm 메일"이라는 말이 정확하지 않다. 디자이너에게 알린다(예: `GIST 메일을 입력해주세요.`).
  - 디자이너가 문구를 바꿀 때까지는 시안 문구를 그대로 쓴다.
- 폼에 `noValidate`를 단다. 지금은 `type="email"`이라 `abc`를 넣으면 브라우저 말풍선이 뜬다. 0장의 "실제 웹 폼, OS 기본 컨트롤 아님" 원칙에 어긋난다. `@`가 없는 값도 같은 문구로 처리한다.
- 서버 패턴 `^[^+]+@`은 `+` 주소를 400으로 막는다. 위 정규식이 `+`를 미리 거르므로, 이 경우에도 도메인 오류 문구가 뜬다. 문구가 딱 맞지는 않지만 드문 경우라 따로 두지 않는다.
- `입력해주세요`(붙여 씀)는 저장소의 `입력해 주세요`와 다르다. 시안 그대로 쓰고 디자이너에게 알리기만 한다.

### 2.4 인증번호 입력 / 만료 / 불일치 → `verify.tsx` `CodeStep`

#### 2.4.1 문구 — P1

#### 2.4.2 410 만료·404 처리 — **P0**

명세(`/verify/code`)의 응답은 **400 틀림(`remaining_attempts`) / 404 진행 중인 요청 없음 / 410 만료**다.

✅ **D2-6 (2026-11-14): 5회 틀리면 그 코드는 무효가 되고, 다음 확인 요청부터 404가 온다.** 그래서 404는 두 경우를 함께 뜻한다.
- 5회를 다 틀려서 코드가 무효가 됨
- 처음부터 진행 중인 인증 요청이 없음

어느 쪽이든 사용자가 할 일은 "새 인증번호 받기"다.

코드는 다음과 같다.
- 410을 처리하지 않는다. 일반 문구 `인증에 실패했습니다. 다시 시도해 주세요.`로 떨어진다(`:321`).
- 404는 `인증번호가 만료됐어요. 새 인증번호를 받아주세요.`로 보여 준다(`:318-319`). 문구 방향은 맞다.
- 404·410을 받아도 `expired`가 false로 남는다. 그래서 버튼이 `인증 확인` 그대로이고, 죽은 코드로 계속 제출할 수 있다.

바꿀 것:
1. `expired = 시계상 만료 || 서버가 404·410을 줌`으로 넓힌다. 둘 다 시안의 만료 화면(만료 문구 `인증 시간이 지났어요. 새 인증번호를 받아주세요.` + `인증번호 다시 받기`)으로 보낸다. 기기 시계가 틀려도 서버 응답이 기준이 된다.
2. 404 문구는 시안의 만료 문구와 같게 맞춘다. 5회 실패 직후에는 바로 앞 응답에 `(0회 남음)`이 이미 보였으므로 사용자가 이유를 안다. 따로 문구를 두지 않는다.
3. 주석: `api/student.ts:76`("5번 틀리면 코드가 무효가 되어 404 로 바뀐다")은 이미 맞다. `verify.tsx`의 `describeVerifyError` 404 분기에는 "5회 실패로 코드가 무효가 되었거나 진행 중인 요청이 없음" 주석을 달았다(2026-11-14).

#### 2.4.3 다시 받는 동안 이메일 화면으로 튐 — **P0 (버그)**

화면 전환을 `send.data`(마지막 mutation 결과)로 정한다(`:67`, `:107`). react-query v5는 `mutate`를 다시 부르면 이전 `data`를 비운다. 그래서 다음 일이 생긴다.

- 만료 화면에서 `인증번호 다시 받기`를 누르면 요청 중 잠깐 **`학교 이메일 인증` 화면(`보내는 중…`)으로 바뀐다.**
- 그때 429가 오면 이메일 화면에 그대로 남는다.

시안은 다시 받는 동안에도 인증번호 화면에 머문다.

→ 마지막으로 성공한 발송 결과(`expires_at`, `resend_available_at`)를 **별도 state**에 둔다(`onSuccess`에서 넣음). 화면 전환은 그 state로 정한다. 다시 받다가 생긴 오류(429 등)는 인증번호 칸의 오류로 보여 준다.

같이 고칠 것(P2):
- 429 대기 시간을 `mmss`로 그리므로, 대기가 1시간을 넘으면 `125:00` 같은 모양이 된다. 명세에 "발송 횟수 초과"도 429로 묶여 있다. 60분 이상이면 `n시간 m분` 형식으로 쓴다.
- 불일치 뒤에 코드를 고쳐 쳐도 오류가 남는다. 값이 바뀌면 `verify.reset()`을 부른다.
- `verify.tsx:16-18` 머리 주석에 이 섹션의 상태 프레임 ID를 모두 적는다(이메일 4상태, 인증번호 3상태).

  - 중복: `이미 추가된 분야예요.`
  - 20개 초과: `+ 기타` 비활성
- **긴 이름:** 칩 폭이 격자로 고정이다. `truncate`로 말줄임하고 `title`에 전체 값을 둔다.
- ✅ **D2-3 (2026-11-14, BE 확인):** `interests`에 **50자 이내 문자열**을 보내면, 서버 목록에 없는 값이어도 받는다. 그 값은 **그 학생의 프로필에만 개인적으로 저장된다.** 서버의 공통 관심 분야 목록(`GET /user/student/interests`)에는 추가되지 않는다. 그래서 FE는 별도 API 없이 고정 칩 값과 사용자 값을 **한 배열에 섞어 보내면 된다.**

  - 내 정보(`profile.interests`)를 다시 받을 때는 위의 `filter`로 사용자 값을 다시 골라낸다. 운영자가 목록에서 어떤 분야를 지우면 그 값을 가진 학생에게는 사용자 칩(연필)으로 보이게 된다. 의도된 동작으로 둔다.

#### 2.6.3 알림 설정 (연락 수단 하나 이상 필수) — **P0**

- 제목: 시안은 `알림 설정 (선택)`(Label/Medium). 레이어 이름은 아직 `연락 설정 (선택)`이다.

모양:

  - 데스크톱: 체크박스 140 + 칸(`flex-1`, 52 높이, `border-control`) 한 줄, 줄 사이 8 (`943:9742`)

### 2.9 작업 체크리스트 (권장 순서)

> **구현 기록 (2026-11-14).** 아래 체크한 항목은 `42-sync-figma-design-service-policy` 작업 트리에 반영했다(커밋 전). 구현하면서 정한 세부 사항:
> - **연락 설정은 03장의 `ContactChannelFields`를 그대로 쓴다.** 학생용으로 `requireOne`(두 채널을 모두 끄면 문구) 하나만 더했다. 폼 값은 선배와 같은 `contact: { kakao, email, phone, emailAddress }`이고 저장도 `contactRequestFrom`을 같이 쓴다. 처음 값은 `studentContactDefaults`(이메일만 켬 + 인증한 메일).
> - **선배에게 보이는 이메일**(전달 프로필 미리보기, 신청 화면 요약, 마이페이지)은 학교 이메일이 아니라 알림 설정에서 켠 주소다(`studentSharedEmailOf`).
> - **첨부 폼 값**은 `{ kind, source: "file", key, fileName, href? } | { kind, source: "link", url }`. 예전 링크 첨부는 줄로 보여 주고 지울 수 있다(지우지 않으면 그대로 다시 보낸다). 새로 올린 파일은 로컬 blob URL로 열 수 있다. 업로드한 파일의 `kind`는 모두 `portfolio`(D2-9).
> - **허용 도메인 검사**(`lib/school-email.ts`)는 `gist.ac.kr`과 그 하위 도메인을 받는다. 서버 목록은 superadmin이 바꾸는 값이라 화면은 덜 막고 400을 예비로 둔다.
> - **고정 관심 분야 칩**은 한 줄(`whitespace-nowrap`)이다. `이차전지/배터리`처럼 칸보다 조금 긴 글자는 시안처럼 좌우 여백으로 넘친다. 길이를 모르는 사용자 칩만 말줄임한다.
> - **바텀시트**는 Base UI Select의 Positioner가 넣는 인라인 위치(`transform`)를 `!`로 덮어서 화면 아래에 붙인다. 리스트박스 동작(키보드, 글자로 찾기, 포커스)은 데스크톱과 같다.
> - **순수 로직 테스트**: 저장소에 테스트 도구가 없어 `bun test`(Bun 내장, 새 의존성 없음)로 `tests/`에 두었다. 이메일 도메인·대기 시간 표기, 기타 관심 분야 추가·수정·삭제, 연락 설정·첨부 변환이 대상이다(35개).
> - 선배 명함 첨부(`mentor/verify.tsx`)의 끌어다 놓기·파일 선택 버튼을 `ui/file-drop.tsx`(`useFileDrop`, `FilePickButton`)로 꺼내 둘이 같이 쓴다.
> - 리뷰에서 고친 것: 기타 관심 분야 대화상자의 제출이 포털을 거쳐 바깥 페이지 폼까지 제출되던 문제(`stopPropagation`), 여러 파일이 같은 순간에 올라가면 앞의 파일이 사라지던 문제, 서버 만료(404·410) 뒤 다시 받기 중·실패 시 만료 화면이 풀리던 문제, 429 대기 중에도 다시 받기가 눌리던 문제.
> - 남은 작은 것(다음 작업 때): MIME이 빈 PDF(일부 Windows 끌어다 놓기)는 `content_type`이 비어 400이 날 수 있음, PDF가 아닌 파일이 빈 자리를 먼저 차지함, 올리는 중 `이전`을 누르면 그 파일이 빠짐, 상자 바깥에 떨어뜨리면 브라우저가 파일을 열어 입력이 사라짐, 받은 신청 상세에서 같은 파일 이름 두 개면 React key가 겹침, `n/3`의 `aria-label`이 `span`이라 안 읽힘, 신청 화면 전화번호 줄이 알림톡 꺼짐을 안 봄(원래 있던 것).
