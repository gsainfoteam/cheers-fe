## 0. 이 문서를 읽는 법

설계 문서는 **시간순 작업 기록**이다. 왜 그렇게 했는지가 전부 들어 있지만, "이 화면을 고치려면 뭘 지켜야 하나" 를 찾으려면 800줄을 다 읽어야 한다. 이 문서는 같은 내용을 **흐름별 규칙**으로 다시 묶고, 설계 작성(11-03) 뒤에 **피그마에 새로 올라온 시안**과 그 시안이 API·현재 코드와 어긋나는 자리를 정리한다.

판단이 갈릴 때의 우선순위:

1. **제품 규칙** — 피그마 `구현·정책 메모`(`344:9344`), 설계 5.3
2. **API 명세** — `openapi.json`. 명세가 막는 UI 는 시안에 있어도 만들지 않는다(그리고 기록한다)
3. **피그마 시안** — 수치·문구·상태
4. 이 문서와 설계 문서의 결정

> 세 흐름의 1차 구현은 끝나 있다(설계 단계 3·4). 아래 §2~§4 의 "남은 작업" 은 그 뒤에 바뀐 시안에서 나온 것이다.

## 1. 모든 화면에 공통인 규칙

### 1.1 반응형

- **폭은 두 개, 경계는 `lg`(1024px) 하나.** 기본 클래스가 모바일(393 시안), `lg:` 가 데스크톱(1440 시안)이다. `md:` 등 다른 경계를 쓰지 않는다.
- **한 화면의 두 폭은 같은 커밋에서 끝낸다.** "모바일은 나중에" 는 금지(설계 4절 안티골).
- 모바일과 데스크톱이 **배치만 다르면** 한 DOM + `lg:` 로, **구조가 다르면**(예: `SignupProgress`) 마크업 두 벌 + `hidden lg:block` 으로 간다. 두 벌일 때 숨긴 쪽은 `display:none` 이어야 보조기술에 두 번 읽히지 않는다.
- 순서만 뒤집히면 `order-first lg:order-last` 로 처리한다. DOM 을 두 벌 쓰지 않는다.

### 1.2 토큰 — 수치를 하드코딩하지 않는다

- 색·그림자·모서리·타이포는 [`src/styles/tokens.css`](../../../src/styles/tokens.css) 의 **Cheers 이름**을 쓴다: `bg-canvas`, `bg-surface`, `text-ink`, `text-ink-soft`, `border-line`, `border-control`, `text-brand`, `shadow-work`, `shadow-modal` …
- `bg-primary`, `border-input` 같은 **shadcn 다리 이름은 새 코드에서 쓰지 않는다.** 단계 5에서 통째로 사라질 수 있는 임시 블록이다.
- **간격은 Tailwind 기본 스케일이 곧 피그마 토큰이다**(`p-4` = 16). `--spacing-*` 를 새로 선언하지 않는다.
- 폭마다 값이 다른 타이포는 **반응형 토큰 하나**로 쓴다: `text-hero`, `text-statement`, `text-task-title`, `text-page`. 호출부에 `lg:` 가 붙지 않는다.
  짝이 토큰에 없을 때만 `text-task-title lg:text-page` 처럼 두 토큰을 갈아 끼운다. `text-[32px]` 같은 임의 값은 쓰지 않는다.
- 토큰에 없는 피그마 값을 꼭 써야 하면 그 자리에 주석으로 이유를 남긴다(예: 랜딩의 `#fffcf8`).

### 1.3 셸과 라우트

- 헤더·푸터는 `PageShell` 이 그리고, **구간을 가진 라우트가 자기 `kind` 를 직접 적는다**(`public` / `onboarding` / `student` / `alumni`). `__root.tsx` 에는 셸이 없다.
  → **공개 라우트를 새로 만들면 `PageShell kind="public"` 을 직접 씌워야 한다.** 이 구조의 유일한 함정이다.
- 가로 폭·좌우 여백은 `PageContainer`(`max-w-page` + `px-5 lg:px-24`)만 쓴다. 배경이 화면 끝까지 가야 하는 섹션은 바깥에 배경, 안쪽에 `PageContainer`.
- **모바일 전체 화면 오버레이에는 셸이 없다.** 그건 라우트가 아니라 `ResponsiveDialog` 가 셸을 덮는 것이다.

### 1.4 데이터와 가드

- **세션의 출처는 `userInfoQuery()` 하나다.** 가드(`lib/guards.ts`)는 `ensureQueryData`, 화면은 `useSession()`/`useSuspenseQuery(userInfoQuery())` 로 같은 캐시를 읽는다. 다른 곳에서 role 을 따로 계산하지 않는다.
- **가드는 레이아웃에만 둔다.** `/onboarding`(단계 가드)과 `/_app`(로그인 + 가입 완료 가드) 두 곳. 하위 화면에 가드를 또 달지 않는다.
- **"다음 화면" 은 화면이 아니라 서버의 `next_step` 이 정한다.** 저장에 성공하면 `router.invalidate()` 만 부르고 가드에 맡긴다. 온보딩 화면에서 다음 경로로 직접 `navigate` 하지 않는다(같은 단계 안에서 화면을 넘길 때만 예외 — 기본 정보 → 추가 정보).
- 응답은 `unwrap(res, Schema)` 로 zod 검증을 거친다. 계약이 어긋나면 `ContractError` 가 나고 `/verify.html` 에서 줄 단위로 볼 수 있다.

### 1.5 공통 컴포넌트

이미 있는 것을 먼저 쓴다. 새 공통 컴포넌트는 **두 번째 사용처가 생길 때** `components/ui` 로 올린다(설계 2절).

| 컴포넌트 | 파일 | 쓰는 곳 |
|---|---|---|
| `action()` | `components/ui/action.ts` | 버튼 생김새(Primary/Secondary/Ghost × md52/lg56). **컴포넌트가 아니라 클래스 함수** — `<button>`·`<Link>` 어디든 붙인다 |
| `Field`, `Select` | `components/ui/field.tsx` | 입력 칸. 시안 5상태 → `error`·`readOnly`·포커스(`focus-within`). `labelHidden` 지원 |
| `Choice` | `components/ui/choice.tsx` | 고르는 칩. 폭은 쓰는 쪽이 정한다(격자 or 글자 길이) |
| `ResponsiveDialog` | `components/ui/responsive-dialog.tsx` | **PC 모달 / 모바일 전체 화면** 오버레이. `className`(데스크톱 크기)·`actions`(버튼 줄) |
| `SignupProgress` | `components/signup-progress.tsx` | 가입 단계 표시(읽기 전용, 링크 아님) |
| `ProfileRow` | `components/ui/profile-row.tsx` | 이름표 112 + 값. `compact`/`comfortable` |
| `EmployeeBadge` | `components/employee-badge.tsx` | 사원증 카드(랜딩·선배 목록) |
| `PageShell`, `PageContainer` | `components/layout/` | 셸·본문 폭 |

### 1.6 오류 문구

- 화면마다 `describeXxxError(error)` 함수 하나에 **HTTP 상태 → 문구** 매핑을 모은다. 명세의 응답 설명(400/403/404/409/429)을 하나씩 대응시킨다.
- 오류 문단은 `role="alert"` + `text-danger`. 색만으로 상태를 말하지 않는다(문구를 같이 바꾼다).
- 시안에 문구가 있으면 **시안 문구를 그대로** 쓴다(§2.3 참고 — 지금 몇 군데 어긋나 있다).

### 1.7 시안과 다르게 둘 때

시안을 따를 수 없는 이유(명세 충돌, 레이어 사고, 접근성)가 있으면:

1. 그 자리 **코드 주석**에 이유를 적고,
2. 설계 문서 해당 단계의 "시안과 다르게 둔 것" 에 한 줄 추가하고,
3. 디자이너/백엔드 확인이 필요하면 **"확인 필요"** 라고 적는다 — 그리고 §5 표에도 올린다.

### 1.8 완료 기준

- `bun run build`(`tsc -b` 포함) / `bun run lint` 통과
- 산출물 CSS 치수를 시안과 대조(설계의 각 "끝난 상태" 처럼)
- **두 폭을 눈으로 확인.** 오버레이가 있는 화면은 **열린 채로 1024px 경계를 넘나들어** 입력값·스크롤이 살아남는지 본다 — 이 설계의 핵심이고, 아직 아무 화면도 눈으로 닫히지 않았다

### 2.2 흐름과 지켜야 할 것

```
랜딩 ──"학생으로 시작하기"──▶ /login?role=student
  └ GIS 콜백 → useLogin({ provider:"google", type, token, nonce })
      ├ redirect 있으면 history.push(redirect)   ← 딥링크 복귀
      └ 없으면 router.invalidate() → 가드가 next_step 으로 보냄
/onboarding (가드: requireSession → next_step → isAllowed)
  consent → /onboarding/terms
  verify  → /onboarding/student/verify   (이메일 ↔ 인증번호, 한 라우트)
  profile → /onboarding/student/profile → /onboarding/student/extra
              └ POST /user/student/info (응답의 새 토큰을 adoptIssuedTokens)
                 → reset() → router.invalidate() → next_step=null → /mentors
```

**로그인**

- 학생·선배 로그인은 **한 라우트**다. 차이는 제목과 전환 링크뿐이고 `role` 검색 파라미터로 가른다. URL 에 role 이 없으면 `lastRole() ?? "student"`.
- `/login` 검색 파라미터 넷(`redirect`, `reason`, `role`, `switchAccount`)은 **전부 선택**이다. 필수로 바꾸면 가드와 딥링크 호출부가 전부 깨진다.
- `switchAccount` 일 때는 세션이 있어도 `redirectIfSignedIn` 을 건너뛴다.
- **구글 버튼 덮개를 건드리지 않는다.** 보이는 건 시안 버튼(`aria-hidden`), 실제로 눌리는 건 그 위의 투명한 GIS 버튼(폭 400 고정 + `transform: scale`). `renderButton` 을 폭에 맞춰 다시 그리거나, 시안 버튼에 `onClick` 을 달면 동작하지 않는다.
- 카카오·네이버는 **비활성으로 표시만** 한다(설계 5.3).

**온보딩 가드**

- 새 온보딩 경로를 만들면 **`lib/onboarding-steps.ts` 의 `PATHS` 에 먼저 등록**한다. 등록하지 않은 경로는 가드가 진입 지점으로 튕겨낸다.
- 배열의 첫 번째가 그 단계의 진입 지점이다. 순서를 바꾸지 않는다.

**본인 확인**

- 이메일 화면과 인증번호 화면은 **한 라우트**다(서버 단계가 `verify` 하나). 발송 결과(`expires_at`)가 있으면 입력 화면.
- **남은 시간은 state 에 담지 않는다.** 타이머는 리렌더를 깨우기만 하고 남은 초는 렌더 때마다 `expires_at` 으로 계산한다.
- 만료가 불일치보다 먼저다. 만료면 주 버튼이 `인증번호 다시 받기` 로 바뀐다. 재전송은 `resend_available_at`/429 의 `retryAvailableAtOf` 까지 잠근다.

**기본 정보 → 추가 정보**

- 두 화면의 값은 **`lib/student-signup-draft.ts`(zustand)** 로 넘긴다. **localStorage 에 남기지 않는다** — 새로고침하면 `extra` 의 `beforeLoad` 가 `hasBasics` 로 알아채고 기본 정보로 되돌린다.
- 저장 성공 시 반드시 `reset()`. 안 하면 계정을 바꿔 가입할 때 남의 값이 올라온다.
- 이름은 `me.name` 이 있으면 읽기 전용 + `가입 후 변경할 수 없어요.`, 없을 때만 입력·필수. 요청에도 `me.name` 이 없을 때만 `name` 을 싣는다.
- 저장 응답에 새 토큰이 온다. `useSubmitStudentInfo` 가 교체하므로 **이 훅을 우회해 직접 POST 하지 않는다**(교체를 빠뜨리면 가입 직후 전부 401).
- 빈 문자열은 400 이다(`email`, `phone`). 값이 없으면 키를 빼거나 `null`.

### 2.3 남은 작업 — 설계 이후 새로 올라온 시안

피그마 `02 · 학생 가입·인증`(`375:15122`) 에 설계 작성 뒤 프레임이 여럿 추가됐다. 아래는 데스크톱 프레임을 기준으로 확인한 것이고, **모바일 짝은 열어보지 못했다** — 구현 전에 모바일 프레임부터 열 것.

### 3.2 지켜야 할 것

- **목록은 index 가 아니라 레이아웃 라우트에 있다.** `mentors.tsx` 가 목록 + `<Outlet/>` 이고 신청(`$mentorId/apply`)이 자식 오버레이다. index 로 옮기면 신청을 열 때 목록이 언마운트돼 모달 뒤가 비고, 스크롤 위치도 날아간다.
- **질의 조건은 `MENTOR_LIST_PARAMS` 하나만 쓴다**(`lib/mentor-list.ts`). 둘러보기·신청·신청 완료 세 화면이 같은 캐시를 봐야 한다. 조건을 화면에서 따로 적으면 다른 목록으로 취급돼 다시 받아온다.

- 격자: 모바일 `grid-cols-2 gap-x-3 gap-y-8`, 데스크톱 `lg:grid-cols-4 lg:gap-x-8 lg:gap-y-10` → 카드 170.5 / 288. 랜딩 갤러리와 같은 수.

  - 상자는 ISO ID-1 비율로 **통째로 확대**된다. 내부 수치는 전부 `--u`(= 시안 1px, `calc(100cqw / 170.5)`)로 적는다.

  - `커피챗 신청` 줄은 카드에 **인쇄되지 않는 웹 UI** 라 사원증 바깥에 붙인다.

## 4. 흐름 C — 커피챗 신청

### 4.2 지켜야 할 것

**오버레이**

- `ResponsiveDialog` 를 쓴다. 이 화면이 정하는 건 **데스크톱 크기(`lg:h-184 lg:w-220` = 880×736)** 와 **`actions`(취소 + 신청 보내기)** 뿐이다. 오버레이 내부 구조(머리 / 스크롤 본문 / 버튼 줄)를 화면에서 다시 만들지 않는다.
- **주 버튼은 스크롤 영역 바깥, 폼은 안쪽.** `<button type="submit" form={formId}>` 로 잇는다. 5.3 의 "주요 버튼은 항상 접근 가능" 을 지키는 구조다.
- 모바일에는 `취소` 가 없다(닫기 X 가 대신) → `hidden lg:flex`.
- 오버레이는 열린 채로만 그린다. **닫기 = `/mentors` 로 이동**이다. 오버레이 안에서 같은 탭으로 다른 곳에 보내면 적던 질문이 사라진다 → FAQ 처럼 바깥으로 나가는 링크는 **새 탭**.

**데이터**

- 선배 정보는 **목록 캐시**(`cheersListQuery(MENTOR_LIST_PARAMS)`)에서 찾는다. 카드 하나를 받는 엔드포인트가 없다. 목록에 없는 id → `선배를 찾을 수 없어요`.
- 질문은 **200자**(명세 `maxLength` = 시안), 앞뒤 공백을 뺀 뒤 비어 있으면 못 보낸다. 서버도 trim 후 검사한다.
- `useRequestCheers` 가 성공 시 `keys.sent` 를 무효화한다. 보낸 신청 목록을 따로 갱신하지 않는다.
- 오류 매핑: 409 `지금은 이 선배가 신청을 받지 않아요`(목록을 받은 뒤 선배가 설정을 바꾼 경우 — `can_request` 만으로는 못 막는다), 404, 403(재학생 아님), 400.
- 선배 계정이 열면 폼 대신 `커피챗 신청은 재학생만 보낼 수 있어요.` 한 줄. 실제 차단은 서버(403).
- `함께 전달되는 내 정보` 는 `ProfileRow`(`compact`) 일곱 줄. 값이 없으면 빈칸 대신 `등록하지 않음`. 이 목록은 §2.3 의 추가 정보 개편(파일 여러 개, 연락 이메일 편집)이 들어오면 **같이 바뀐다** — 특히 `이력서 / 포트폴리오` 는 지금 첫 번째 첨부만 보여준다.

**신청 완료**

- 오버레이가 아니라 셸을 두른 한 장이다. 그래서 경로가 **`mentors_`**(밑줄 = 부모 레이아웃을 쓰지 않음). 주소는 `/mentors/{id}/sent` 그대로.

**제품 규칙 (설계 5.3 — 임의로 바꾸지 않는다)**

- 신청은 **확정이 아니다.** UI 가 그렇게 읽히면 안 된다. 연락처 공유도 수락·일정 확정이 아니다.
- 읽음·거절·만료·취소 기능은 **의도적으로 없다.** 명세가 `requested / viewed / contact_shared` 를 줘도 상태 배지를 그리지 않는다.
- 로그아웃 상태로 신청 링크에 들어오면 `/login?redirect=…&reason=application` 으로 갔다가 같은 자리로 돌아온다(가드가 처리 — 화면에서 따로 할 일 없음).
