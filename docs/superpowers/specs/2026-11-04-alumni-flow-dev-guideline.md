## 0. 이 문서를 읽는 법

학생 줄기는 설계 단계 3·4에서 1차 구현이 끝났고, 학생 가이드가 그 규칙을 흐름별로 묶었다. 선배 줄기는 **설계 3절이 비목표로 미뤄 둔 구간**이라 지금 화면이 전부 자리표시(`<div>명함 첨부 및 인증</div>` 같은 9줄 파일)다. 설계 단계 5가 예상한 대로 *"같은 패턴의 반복"* 으로 채울 수 있는지, 그리고 **어디서 패턴이 깨지는지**를 미리 정리하는 것이 이 문서의 목적이다.

## 1. 공통 규칙 — 학생 가이드 §1 을 그대로 따른다

반응형(`lg` 하나, 두 폭 같은 커밋), 토큰(Cheers 이름, shadcn 다리 금지, 기본 간격 스케일), 셸(`PageShell kind`), 데이터·가드(`userInfoQuery()` 하나, 가드는 레이아웃에만, 다음 화면은 `next_step`), 오류 문구(`describeXxxError` + `role="alert"`), 시안과 다르게 둘 때의 기록 방법, 완료 기준 — **전부 학생 가이드 §1.1~§1.8 과 같다.** 여기서는 선배 줄기에서 추가되거나 달라지는 것만 적는다.

### 1.1 선배에게만 해당하는 것

- **이름이 셋이다.** 서버는 `graduated`(`me.type`), 세션·로그인 URL 은 `mentor`(`lib/role.ts`, `/login?role=mentor`), 헤더는 `alumni`(`HeaderKind`), 화면 문구는 `선배`. 새 이름을 만들지 말고 자리마다 이미 쓰는 쪽을 따른다. 경로는 `/onboarding/mentor/*` 다.
- **선배 화면은 `role !== "mentor"` 분기가 아니라 라우트 loader 에서 `me.type` 으로 가른다.** 학생·선배가 같은 경로(`/applications`, `/me`)를 쓰고 API 가 다르다. 화면에서 분기하면 loader 가 엉뚱한 API 를 불러 403 화면이 뜬다(설계 4-3c 가 겪은 문제).
- **가입을 마친 뒤 가는 곳은 학생·선배 모두 `/mentors` 다.** 백엔드가 선배에게도 선배 목록을 열었다(§3.1, 2026-11-05). 세 군데(`routes/onboarding.tsx:23`, `lib/guards.ts:94`, `SiteHeader` 의 로고)가 각자 적고 있지만 값이 같으므로 지금은 그대로 둔다.
- **명함 인증은 취소될 수 있다.** 명세: *"어드민이 명함 인증을 취소한 active 현업자는 `next_step = verify`"*. 가입을 마친 선배도 어느 날 `/onboarding/mentor/verify` 로 돌아온다. `_app` 가드가 이미 그렇게 보내므로 따로 할 일은 없지만, 명함 첨부 화면이 **"처음 가입" 과 "재인증" 둘 다** 를 맞는 문구로 보여야 한다(§2.5 참고). 받은 신청 API 의 403 *"명함 인증이 취소됨"* 은 캐시가 낡았을 때만 보인다 — `describeXxxError` 에 문구를 두고 `router.invalidate()` 로 가드에 맡긴다.

### 1.2 이미 있는 것 중 선배 화면이 그대로 쓰는 것

### 2.2 흐름과 지켜야 할 것

```
랜딩 ──"취업했어요, 경험을 나눌래요"──▶ /login?role=mentor
  └ GIS 콜백 → useLogin(…)   (학생 로그인과 같은 코드, role 만 다르다)
/onboarding (가드: requireSession → next_step → isAllowed)
  consent → /onboarding/terms                         (학생과 같은 화면)
  verify  → /onboarding/mentor/verify
              ① 파일 고르면 uploadFile("business_card") → key
              ② `다음` → useVerifyBusinessCard({ key }) → router.invalidate()
  profile → /onboarding/mentor/profile → /onboarding/mentor/extra
              └ POST /user/graduated/info (새 토큰 adoptIssuedTokens)
                 → reset() → router.invalidate() → next_step=null → /mentors
```

- `lib/onboarding-steps.ts` 의 `PATHS.graduated` 는 **이미 등록돼 있다.** 세 경로를 새로 만들 일은 없고 화면만 채우면 된다.
- 약관은 유형과 무관하게 한 화면이다. 시안의 선배판(`339:9326`)도 `전체 동의` / `[필수] 서비스 이용약관` / `[필수] 개인정보 수집·이용 동의` / `동의하고 다음` 으로 학생판과 같다(화면으로 확인). **고칠 것 없음.**

### 2.3 명함 첨부 (`/onboarding/mentor/verify`)

**화면.** 점선 업로드 상자 + 아래 주 버튼 `다음`. 데스크톱은 작업 영역 976(352 + 64 + 560)의 카드 안, 모바일은 **카드 껍데기 없이** 캔버스 위에 점선 상자가 바로 놓인다 — 학생의 약관·본인 확인과 같은 뼈대다. 제목 `명함 첨부`, 설명 `회사와 이름을 확인할 수 있는 명함 이미지 1장을 첨부해 주세요.`

| 상태 | 업로드 상자 | 주 버튼 `다음` |
|---|---|---|
| 비어 있음 · 데스크톱 | 점선 + `명함 이미지를 여기에 끌어다 놓거나,` / `파일 선택 버튼을 직접 선택해주세요.` + `파일 선택`(아이콘 `media-image-plus`) | 비활성 |
| 비어 있음 · 모바일 | 점선 + `명함 이미지를 선택해주세요.` + `파일 선택` — **끌어다 놓기 문구가 없다** | 비활성 |
| 드래그 중 (데스크톱) | 점선이 **실선 주황 테두리 + 옅은 주황(champagne 계열) 바탕**으로 바뀐다. 문구·버튼은 그대로 | 비활성 |
| 올리는 중 | 시안 없음 — 버튼 `aria-busy` + 문구 정도로 | 비활성 |
| 완료 | 상자 자리에 명함 미리보기 + 그 아래 `다른 이미지 선택` | **활성**(Primary) |
| 오류 | `이미지를 올리지 못했어요.` / `다시 첨부해 주세요.` (`text-danger`) + `파일 선택` | 비활성 |

문구가 폭마다 다르므로 두 문장을 `hidden lg:inline` / `lg:hidden` 으로 갈아 끼운다. 모바일에는 끌어다 놓을 손이 없다는 뜻이지 기능을 막으라는 뜻은 아니다 — 드롭 이벤트는 폭과 무관하게 받는다.

**지켜야 할 것**

- **업로드는 파일을 고르는 순간, 인증은 `다음` 에서.** 시안이 오류를 `다음` 전에 업로드 상자 안에 그린다. 그래서 고르자마자 `uploadFile("business_card", file)` 로 key 를 받아 두고, `다음` 에서 `useVerifyBusinessCard({ key })` 를 부른다. 3번까지 안 간 tmp 파일은 하루 뒤 서버가 지우므로 정리할 필요가 없다(`api/file.ts` 주석).
- **S3 PUT 에는 `api` 클라이언트를 쓰지 않는다.** `uploadFile` 이 이미 `fetch` 로 처리한다 — Authorization 헤더가 붙으면 서명 불일치로 403 이다. 이 함수를 우회하지 않는다.
- 다른 파일로 바꾸면 이전 업로드를 `AbortController` 로 끊는다. 늦게 끝난 이전 업로드가 새 key 를 덮어쓰면 엉뚱한 명함이 인증된다.
- 미리보기는 서버 URL 이 아니라 **로컬 `URL.createObjectURL(file)`** 이다(본인 명함을 다시 받는 API 가 없다). 바꾸거나 떠날 때 `revokeObjectURL`.
- 미리보기 비율: 시안 `922:43811` 이 규칙을 예시 여섯 장으로 그려 뒀다.

  | 폭 | 상자 비율 | 상자보다 세로로 긴 이미지 | 같은 비율 | 가로로 긴 이미지 |
  |---|---|---|---|---|
  | 데스크톱 | **1 : 1.64** (480×292) | 높이에 맞춤 | 꽉 참 | 폭에 맞춤 |
  | 모바일 | **1 : 1.33** (353×265) | 높이에 맞춤 | 꽉 참 | 폭에 맞춤 |

  즉 **상자 비율은 폭마다 다르고, 그 안에서는 `object-contain`** 이다. `aspect-[4/3] lg:aspect-[1.64/1]` 같은 식으로 상자만 바꾸면 되고, 이미지 비율을 JS 로 재서 분기하지 않는다. 남는 자리는 시안이 체크무늬로 그려 뒀는데 투명을 표현한 것이므로 바탕은 상자 배경색(토큰)으로 둔다.
- 오류 매핑: 발급 단계의 400(허용되지 않은 형식)·413(크기 초과), S3 실패, 인증 단계의 400(key 불일치·업로드 안 됨) — 시안 문구는 하나뿐이다. **문구는 시안 그대로 두고**, 형식·크기만 구분해 줄지는 디자이너 확인(§7 #6). 파일 크기 상한을 클라이언트에 하드코딩하지 않는다(서버가 413 으로 알려준다).
- `<input type="file" accept="image/*">` 는 숨기고 `파일 선택` / `다른 이미지 선택` 버튼이 `click()` 한다.
- 인증 성공 후 `useVerifyBusinessCard` 가 `refetchType: "all"` 로 내 정보를 다시 받는다(학생 인증에서 겪은 문제를 이미 막아 둔 것 — 커밋 `6581648`). 그 뒤 `router.invalidate()` 만.

**지켜야 할 것**

- **이름은 학생과 같은 규칙**(학생 가이드 §2.2): `me.name` 이 있으면 읽기 전용, 없을 때만 입력·필수, 요청에도 그때만 싣는다. 시안의 빈 상태가 이름을 **입력 칸**으로 그린 것이 바로 `me.name` 이 null 인 경우다.
- **닉네임 형식은 클라이언트에서 먼저 막는다.** 명세 패턴과 시안 메모(`960:10011` *"가-힣, A-Z, a-z, 0-9, _ 만 사용 가능 / 2~10자 길이 제한"*)가 일치한다. zod 스키마에 같은 정규식을 둔다. 오류 문구는 두 가지가 그려져 있다:

  | 상태 | 문구 (화면으로 확인) |
  |---|---|
  | 쓸 수 없는 글자 | `닉네임에 {공백}을 사용할 수 없어요.` — `{공백}` 은 **자리표시**다. 걸린 글자 종류(공백, 특수문자 …)로 바꿔 끼운다 |
  | 이미 사용 중 | `이미 사용 중인 닉네임이에요.` |
  | 길이(2~10자) 위반 | **시안에 문구가 없다** — 디자이너 확인(§7 #3) |

  글자 종류를 가르는 것은 패턴 하나로는 안 된다. "공백이 있나 → 그 밖에 허용 밖 글자가 있나 → 길이" 순서로 검사해 첫 번째로 걸린 이유 하나만 보여준다. 받침에 따라 `을/를` 이 바뀌므로(`공백을` / `특수문자를`) 자리표시에 조사까지 같이 넣는다.
- **"이미 사용 중" 은 명세가 받쳐주지 않는다.** 중복 확인 엔드포인트가 없고, `graduated/info` 의 400·403 설명에도 중복이 없다. 게다가 닉네임은 **추가 정보 화면의 마지막 저장**에서야 서버에 간다 — 중복을 알게 되는 시점이 한 화면 뒤다. 백엔드 확인 전에는 상태만 `Field` 에 준비하고, 저장 응답에 중복 오류가 오면 기본 정보로 되돌려 그 칸에 띄운다(§7 #3).
- **회사명은 검색해서 고르는 칸이다** — 아래 2.4a.
- **`이전` 버튼** — 앞 단계(명함 첨부)는 이미 끝났고 `next_step=profile` 이면 명세가 명함 제출을 403 으로 막는다(*"가입 중인데 next_step이 verify가 아님"*). 학생 기본 정보의 `이전`(설계 3-5d)과 같은 문제라 **같은 결정**을 따른다 — 지금 학생 쪽은 뺐고 "디자이너 확인 필요" 다.
- 두 화면의 값은 **`lib/mentor-signup-draft.ts`(zustand, 새로 만든다)** 로 넘긴다. 규칙은 학생 `student-signup-draft` 와 같다: localStorage 에 남기지 않고, `extra` 의 `beforeLoad` 가 `hasBasics`(`company`·`department`·`job`·`nickname`, 그리고 `me.name` 이 null 이면 `name`)로 알아채 기본 정보로 되돌리고, 저장 성공 시 `reset()`.
  학생 것과 합쳐 제네릭으로 만들지 않는다 — 필드가 하나도 안 겹친다.

`971:10278`(데스크톱) / `971:12664`(모바일), 칸 상태 `971:13884`·`971:13905`·`971:13948`. 피그마 TODO `889:31013` *"회사명 같은 회사 다른 표기 방지하는 디자인"* 의 답이다 — 삼성전자 / 삼성 전자 / Samsung 이 서로 다른 회사로 갈리지 않게 **목록에서 고르게** 한다.

|---|---|---|

- ⚠️ **회사 목록 API 가 없다.** 명세의 `company` 는 자유 문자열이고 회사 목록·검색·등록 엔드포인트가 전혀 없다. 위 표의 별칭 검색(마이크로 → Microsoft)은 별칭 데이터가 있어야 하므로 **클라이언트가 흉내 낼 수 없다.** 백엔드에 목록(별칭 포함) 검색 API 와 `등록하기` 의 뜻(공용 목록에 추가인지, 내 값으로만 저장인지)을 물어야 한다(§7 #2).
- **API 가 오기 전의 임시안**: 컴포넌트는 시안대로 만들되 결과 목록을 비워 두면 **모든 입력이 `등록 정보가 없습니다.` → `+ {입력값} 등록하기` 로 떨어진다.** 이 버튼이 입력값을 `company` 로 확정하면 명세(자유 문자열)와도 맞고 시안 흐름도 깨지지 않는다. API 가 생기면 결과 칩만 채우면 된다.
- 자모 검색을 클라이언트에서 해야 한다면 한글을 자모로 풀어 앞부분을 비교해야 한다(`삼성ㅈ` 은 `String.prototype.startsWith` 로는 안 걸린다). 서버가 검색해 주는 쪽이 낫다 — 별칭과 같은 자리에서 처리되기 때문이다. IME 조합 중(`compositionstart`~`end`)에도 입력값으로 검색하도록 `onChange` 를 쓰고, 요청은 디바운스한다.
- **한 컴포넌트, CSS 로 두 모드.** 학생 가이드 §2.3 의 학과 선택(데스크톱 드롭다운 ↔ 모바일 바텀시트)과 같은 계열이고, 이번 것은 데스크톱 "칸 펼침" ↔ 모바일 "전체 화면" 이다. 검색어·선택값은 부모 상태에 두어 **열린 채로 1024px 경계를 넘어도 사라지지 않게** 한다. 모바일 전체 화면은 `ResponsiveDialog` 의 모바일 모드와 같은 껍데기(머리 + ✕ + 스크롤 본문)이므로 거기서 빌려 쓸 수 있는지 먼저 볼 것.
- 결과 칩은 `Choice` 가 아니다 — 선택 상태(체크·주황 바탕)가 없고 누르면 바로 확정되며 패널이 닫힌다. 칩 모양만 비슷하다.
- 키보드: 화살표로 칩 사이 이동, Enter 확정, Esc 닫기. `@base-ui/react` 의 Combobox 를 쓰면 이 동작과 `aria-activedescendant` 를 공짜로 얻는다. 칩이 가로로 흐르므로 위/아래 화살표의 의미는 정해야 한다(왼/오른쪽만으로도 충분).
- 확정된 값은 펼침이 닫힌 칸에 그대로 보이고(`960:9668` 의 `삼성전자`), **아이콘이 돋보기에서 쐐기(chevron-down)로 바뀐다.** 다시 누르면 같은 검색어로 다시 열린다.

### 2.5 명함 재인증 — 시안에 없는 경우

§1.1 의 *"어드민이 인증을 취소한 active 현업자"* 는 이미 프로필이 있는 사람이다. 그런데 `next_step=verify` 로 돌아오면 같은 명함 첨부 화면을 보고, 그 뒤 `next_step` 이 `null` 이 되는지 `profile` 이 되는지는 명세에 없다.

- 그 뒤 단계는 가드에 맡기면 된다 — `profile` 로 오면 기본 정보가 비어 있지 않게 `me.graduated.profile` 로 초안을 채울 것.

### 2.7 연락 설정 — 시안과 명세가 어긋난다

시안은 선배의 연락처를 **두 용도로 나눴다.**

- `공유할 연락처` = 이메일(필수). *"연락처 공유를 선택한 학생에게만 이름과 함께 전달돼요."* — 선배가 `내 연락처 공유` 를 누르면 학생에게 간다.
- `신청 알림` = 휴대폰(선택). 알림톡을 **받는 번호**이고 *"등록한 번호로 신청 알림을 보내요. 학생에게 공유되지 않아요."*(추가 정보, 화면으로 확인), *"알림 번호는 학생에게 공유되지 않아요."*(마이페이지), *"알림톡 수신 번호는 공유되지 않아요."*(공유 확인).

시안이 같은 말을 세 화면에서 반복한다 — **휴대폰은 절대 공유되지 않는다**가 디자인 의도다.

명세의 `ContactRequestDto` 는 학생과 같은 모양(`email_enabled`, `kakao_enabled`, `email`, `phone`)이고, 공유 응답 `ShareContactResponseDto` 는 **`shared_email` 과 `shared_phone` 을 둘 다** 돌려준다. 즉 명세만 보면 휴대폰도 공유될 수 있다. 또 `CheersCardDto.can_request` 는 *"연락 설정이 희망하지 않음이면 false"* 인데, 시안의 선배 추가 정보에는 **"희망하지 않음"(둘 다 끄기)을 고를 자리가 없다.**

| 질문 | 막히는 것 |
|---|---|
| `kakao_enabled=true` 인 선배가 공유하면 `shared_phone` 이 학생에게 가는가? | 공유 확인 문구 `알림톡 수신 번호는 공유되지 않아요.` 가 거짓이 될 수 있다 |
| 시안의 두 칸을 `email_enabled`/`kakao_enabled` 에 어떻게 매핑하는가(값이 있으면 true?) | 추가 정보·정보 수정 저장 |
| 선배가 신청을 끄는("희망하지 않음") UI 는 어디에 있는가 | `can_request=false`, 공유 409 |

**질문은 이슈 [#26](https://github.com/gsainfoteam/cheers-fe/issues/26) 으로 올렸다(2026-11-05).** 답이 나올 때까지는 아래 **임시 결정**으로 구현한다.

> **임시 결정 — 이메일과 휴대전화번호를 둘 다 받아야 넘어간다.**
>
> | 항목 | 값 |
> |---|---|
> | 요청 | `contact: { email_enabled: true, kakao_enabled: true, email, phone }` |
> | 휴대전화번호 칸 | 라벨에서 `(선택)` 을 뗀다 — `알림 받을 휴대전화번호` |
> | 버튼 | 이메일·휴대폰 둘 다 형식에 맞아야 `가입 완료`(정보 수정은 `변경 내용 저장`) 활성 |
> | 형식 오류 문구 | 이메일은 학생 화면과 같은 규칙, 휴대폰은 시안 `휴대전화번호 형식을 확인해 주세요.` |
> | 결과 | 선배는 "희망하지 않음" 이 될 수 없다 → `can_request` 는 항상 `true` |
>
> 시안과 달라지는 곳은 휴대폰 칸의 `(선택)` 하나다. 코드에는 그 자리에 `// 임시: 이슈 #26 — 둘 다 필수` 주석을 남기고, 설계 문서의 "시안과 다르게 둔 것" 에 한 줄 적는다. 답이 나오면 이 블록과 주석을 함께 걷어낸다.

이 결정은 `shared_phone` 문제(위 표 첫 줄)를 **풀지 않는다** — 휴대폰을 반드시 받으므로 오히려 공유 때 함께 갈 가능성이 생긴다. 그래서 공유 확인(§4.5)의 `알림톡 수신 번호는 공유되지 않아요.` 문구는 #26 의 1번 답이 나오기 전까지 **실제 응답의 `shared_phone` 이 null 인지 스테이징에서 확인한 뒤에** 그대로 둔다. null 이 아니면 그 문구와 버튼 `이름·이메일 공유` 를 바로 고쳐야 한다.

### 3.1 선배도 이 목록을 읽을 수 있다 — 백엔드가 열었다 (2026-11-05 확인)

1-1 에는 추가 검토가 붙어 있다: **로고 비율**(가로형 5:1 · 정방형 1:1 · 세로형 1:2 — `규격 테스트 / 기업 로고 아님`)과 **긴 글자**(닉네임 `반도체연구선배` 7자, 회사명 `한국첨단반도체연구소`).

**선배 화면에 미치는 것 — 어느 안이 되든**

- ⚠️ **"신청 버튼은 카드에 인쇄되지 않는다" 는 지금의 규칙이 뒤집힌다.** 지금 `EmployeeBadge` 컴포넌트 설명(*"Request CTA is separate web UI, not printed on the card"*, 설계 3-1a)과 §3.2 의 "신청 줄은 사원증 **바깥**" 이 둘 다 이 규칙 위에 서 있다. 두 후보 모두 신청 줄을 카드 테두리 **안**에 넣었다.
- ⚠️ **선배 시점 · 마이페이지 · 미리보기 판이 그려져 있지 않다.** 두 후보 모두 학생 시점(헤더 `보낸 신청`, 신청 줄 있음)만 있다. 신청 줄이 카드 안으로 들어오면, 선배 시점(§3.2)에서 그 줄을 빼면 **카드 아래가 비거나 카드 높이가 달라진다** — 지금처럼 "바깥 줄만 안 그리면 되는" 일이 아니다. 선배 시점에서 그 자리에 무엇을 둘지(빈 칸 · 높이 줄임 · 다른 정보) 디자이너 확인이 필요하다.
- **공개 사원증 미리보기(§5.5)는 "다른 회원에게 보이는 사원증" 이다.** 새 사원증에서 학생에게 보이는 모습에 신청 줄이 포함되므로, 미리보기에도 신청 줄을 **누를 수 없는 상태로** 보여줄지 정해야 한다(§7 #18).
- ⚠️ **회사 로고 자리가 커졌다.** 두 후보 모두 로고가 이름만큼 눈에 띄는 자리에 있고, 1-1 은 로고 비율 검토까지 했다 — 로고를 실제로 받을 생각이라는 뜻이다. 그런데 명세(`CheersCardDto`, `GraduatedProfileDto`)에 **로고 필드가 없다**(§3.2 · 설계 4-1c). 로고 없는 카드에서 그 자리가 어떻게 보이는지가 시안에 없다. §2.4a 의 회사명 목록 API 가 생기면 회사별 로고를 함께 줄 수 있는지 백엔드에 같이 물을 것(§7 #2·#18).
- 카드 전체가 아니라 **신청 줄이 상호작용 단위**다(호버·포커스가 신청 줄에만 걸린다). 카드 전체를 링크로 감싸지 않는다 — 학생 가이드 §3.2 의 "신청 줄만 누른다" 와 같다.

**지금 할 일**

- 아무것도 바꾸지 않는다. 단, **사원증을 쓰는 곳을 늘릴 때 `EmployeeBadge` 한 곳만 거치게** 한다(§5.3 의 매핑 함수 승격). 리디자인이 확정되면 그 컴포넌트와 매핑 함수만 고치고 랜딩·선배 둘러보기(두 시점)·마이페이지·미리보기를 같이 확인한다.
- 선배 시점을 지금 만들 때 신청 줄 유무를 `MentorCard` 한 곳에서 가르게 두면(§3.2), 리디자인 때 그 분기가 카드 **안**으로 옮겨 가기만 하면 된다.

  - 포트폴리오는 `attachments` 배열이다. 시안은 한 줄(`portfolio.example.com` — 스킴 없이 도메인만 보인다)이므로 지금은 첫 항목, 학생 가이드 §2.3 의 파일 첨부(최대 3개)가 들어오면 같이 바꾼다. `source: "file"` 의 `url` 은 presigned URL 이라 **만료된다** — 링크를 렌더 시점에 캐시해 두지 말고, 누를 때 오래됐으면 상세를 다시 받는다. 파일이면 URL 대신 `file_name` 을 보인다.
- `410` 은 학생이 탈퇴했거나 유예 중. 목록에서 막지만 딥링크로 들어올 수 있으니 `describeReceivedError` 에 문구를 둔다.

**연락 방법 — 두 카드** (`Cheers / Contact choice`, `338:7636`, 새 컴포넌트)

| 카드 | 시안 | 동작 | 시안에 없는 상태 |
|---|---|---|---|
| 학생에게 직접 연락 | `학생의 이메일로 먼저 연락해요.` + 학생 이메일 + `이메일로 연락하기` | `mailto:` 링크(`<a>` 에 `action()` 클래스) | `student.email` 이 null 일 때 |

#### 4.7a 로그인 필요 — `/login` 의 다른 모양

지금은 가드(`lib/guards.ts` 의 `toLogin`)가 `/login?redirect=/applications/{id}&reason=application` 으로 보내고, 로그인 화면은 **평소의 2열 로그인**(`선배로 시작하기` 제목 + 카드) 안에 한 줄 `신청 내용을 보려면 로그인을 해주세요.` 만 더 보여준다. 시안은 **전혀 다른 한 장**이다.

- **같은 라우트에서 모양만 바꾼다.** `login.tsx` 가 `reason === "application"` 이면 2열 대신 `AccessMessage` 를 그린다. 복귀(`redirect` → `history.push`), 구글 버튼 덮개(학생 가이드 §2.2 — 투명 GIS 버튼 + `transform: scale`)는 그대로 쓴다. 새 라우트를 만들지 않는다 — 복귀 로직과 GIS 덮개를 두 벌 갖게 된다.
- 지금의 `MESSAGE.application` 한 줄은 지운다(시안 문구가 제목·설명·안내로 나뉘어 들어갔다).
- **학생·선배 전환 링크가 없다.** 시안에 `취업 준비 중인 학생으로 시작하기` 가 없다 — 알림톡을 받은 사람은 이미 가입한 선배이기 때문이다.
- ⚠️ **로그인 유형(`role`)을 정해야 한다.** `POST /user/oauth/login` 은 `type` 을 필수로 받고, 지금 이 경로는 `lastRole() ?? "student"` 로 떨어진다. 알림톡을 **새 기기에서 처음** 열면 `lastRole()` 이 없어 **학생 유형으로 로그인을 시도**한다. 이슈 #20 이 이 문제를 다루고 있고, 거기 인용된 명세에 따르면 **가입을 마친(`active`) 유저는 서버가 `type` 을 무시**한다 — 알림톡을 받는 선배는 이미 가입을 마쳤으므로 실제 피해는 없다. 그래도 시안 문구가 `선배 계정으로` 라고 못박은 화면에서 학생 유형을 보내는 건 위험하다. `reason === "application"` 이면 **`role` 을 `mentor` 로 고정**하기를 권장하고, 서버 동작은 백엔드 확인(§7 #16).
- ⚠️ **학생이 받는 알림톡**(선배가 연락처를 공유했을 때 등)도 같은 `/applications/{id}` 로 들어온다면 이 화면의 `선배 계정으로` 문구가 틀린다. 로그아웃 상태에서는 누가 받은 링크인지 알 수 없다. 학생용 알림톡이 있는지, 있다면 링크에 유형을 실어 줄 수 있는지(`?role=student`) 확인(§7 #16). 실어 주면 가드가 `toLogin` 에서 그대로 넘기면 된다.
- 카카오·네이버 버튼이 시안 레이어에 **숨김**으로 들어 있다(`Disabled / provider not available`, `hidden`). 평소 로그인과 달리 **그리지 않는다.**

#### 4.7b 다른 계정 · 접근 불가 — 상세의 오류 화면

지금 `$applicationId.tsx` 의 `RouteErrorComponent` 가 이 역할을 한다(학생 보낸 신청용으로 먼저 만들어졌다). 403 이면 `이 계정에서는 신청을 확인할 수 없어요.` + `다른 계정으로 로그인` 링크(`reason: "wrong-account"`, `switchAccount: true`), 410 이면 `상대가 탈퇴해 신청 내용을 볼 수 없어요.`, 나머지 `신청을 불러오지 못했어요.` — **구조는 이미 시안과 같은 생각**이다. 선배 쪽은 이것을 시안 모양으로 바꾼다.

**어떤 응답을 어느 화면으로** — 선배가 부르는 `GET /cheers/received/{id}` 기준:

| 응답 | 명세 설명 | 화면 |
|---|---|---|
| 404 | *"요청이 없거나 내가 받은 요청이 아님"* | **다른 계정** |
| 410 | *"재학생이 탈퇴했거나 탈퇴 유예기간 중"* | **접근 불가** |
| 400 | *"id가 UUID 형식이 아님"* (링크가 잘림) | **접근 불가** |
| 403 | *"가입을 마치지 않음, 현업자가 아님, 명함 인증이 취소됨"* | 가드가 먼저 온보딩으로 보낸다. 여기까지 오면(학생 계정이 선배 링크를 연 경우 — 학생 loader 는 `sent/{id}` 를 불러 404 를 받는다) **다른 계정** |
| 5xx·네트워크 | — | 지금처럼 `신청을 불러오지 못했어요.` (시안 없음) |

- ⚠️ **404 하나에 "없는 신청" 과 "남의 신청" 이 섞여 있다.** 서버가 구분해 주지 않으므로 둘 다 **다른 계정** 으로 보낸다 — 알림톡으로 들어온 경우 가장 흔한 원인이 계정 불일치이고, 이 화면의 `받은 신청 목록` 버튼이 "없는 신청" 일 때의 출구도 된다. 지금 코드는 403 만 다른 계정으로 보내므로 **404 를 추가**해야 한다. 학생 쪽도 같은 판단이 맞는지는 학생 가이드에서 확인할 일이다.
- `다른 계정으로 로그인` 은 지금 코드의 링크 그대로(`redirect` = 같은 주소, `reason: "wrong-account"`, `switchAccount: true`). `switchAccount` 가 GIS 자동 선택을 끄므로 계정 선택 창이 뜬다 — 이게 없으면 구글이 같은 계정으로 즉시 돌려보내 이 화면을 맴돈다(`login.tsx` 주석). 단 `reason: "wrong-account"` 로 간 로그인 화면은 시안이 없다 — 4.7a 의 `AccessMessage` 모양을 `다른 계정으로 로그인해 주세요.` 문구로 같이 쓰기를 권장.
- **시안은 목록이 없는 한 장인데 코드는 목록 위 모달이다.** 오류 컴포넌트는 `/applications` 레이아웃의 `<Outlet/>` 자리에서 그려지므로 뒤에 목록이 깔린다. 지금 코드 주석(`RouteErrorComponent` 위)이 *"전용 경로로 튕기면 원래 목적지를 또 search param 으로 들고 다녀야 하고, 계정을 바꾼 뒤 같은 URL 을 다시 연다는 단순한 복귀가 불가능해진다"* 고 이 구조를 택한 이유를 적어 뒀다. 그 이유가 여전히 맞으므로 **경로는 그대로 둔다.** 남는 선택은 "뒤에 목록이 보이느냐" 뿐이다.
  - **권장 — 모달 안에 `AccessMessage` 내용을 넣는다.** 지금처럼 목록 위 `ResponsiveDialog` 를 쓰되 안에 시안의 아이콘·제목·설명·버튼을 그대로 넣고, "시안과 다르게 둔 것" 에 기록한다. 뒤에 보이는 것은 지금 로그인한 계정 **자기의** 받은 신청 목록이라 문제가 없다.
  - 시안대로 목록 없는 한 장을 원하면 `applications.tsx` 레이아웃이 자식 매치의 오류 상태를 보고 목록을 숨겨야 하는데, TanStack 에서 깔끔하지 않다. 디자이너가 꼭 한 장을 원하는지 확인 후 결정(§7 #17).
- 접근 불가의 410 은 목록에서 `student_withdrawn` 행을 막은 것(§4.3)과 같은 경우다. 목록을 거치지 않은 딥링크에서만 보인다.

## 8. 권장 구현 순서

설계 1절의 원칙(되돌아가는 일이 가장 비싸다)을 따라, **다른 화면이 기대는 것부터.**

1. **선배 계정으로 `/mentors` 가 열리는지 확인** — 백엔드가 열었다(§3.1). 스테이징에서 직접 확인한 뒤 2번으로. 막혀 있으면 2번 이후를 선배 계정으로 끝까지 확인할 수 없다.
2. **명함 첨부** — 업로드 상자를 여기서 만든다. 가입 줄기의 입구.
3. **기본 정보 → 추가 정보** — `mentor-signup-draft`, 회사명 검색 칸(§2.4a, 결과 없이 `등록하기` 만 동작하는 상태로 시작), 태그 입력. §7 #1·#2 답이 없으면 추가 정보의 저장 매핑만 주석으로 임시 결정.
4. **받은 신청 목록 → 내용 → 공유 확인 → 공유 완료** — `request-item` 승격, `confirm-dialog` 신설, `route-overlay.tsx` 삭제. → ✅ (2026-11-05)
5. **알림톡 진입(§4.7)** — `access-message` 신설, 로그인 화면의 `reason=application` 모양, 상세 오류 화면에 404 추가. 4번의 상세가 있어야 "로그인 후 같은 신청으로 복귀" 를 끝까지 확인할 수 있다. → ✅ (2026-11-05). 실제 알림톡 링크로 로그인 → 복귀는 아직 못 해 봤다
6. **마이페이지 라우트 구조 변경(§5.2) → 마이페이지 → 미리보기 → 정보 수정** — 정보 수정은 3번의 칸 묶음을 재사용하므로 마지막.
7. **선배 둘러보기 선배 시점(§3.2)** — 목록 API 는 열렸으므로(§3.1) 언제 해도 되지만, 다른 화면이 기대지 않는 마무리라 마지막. → ✅ 2·3번(가입)과 함께 먼저 끝냈다 (2026-11-05).

각 단계가 끝나면 설계 문서 7절에 학생 단계처럼 "끝난 상태" 를 기록한다.
