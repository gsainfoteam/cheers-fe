# 반응형 UI 구현 설계 — 모바일/데스크톱

작성일: 2026-11-02
대상 독자: 이 저장소에서 UI를 구현할 프론트엔드 개발자

## 1. 의도와 배경

취얼스 프론트엔드는 **로직이 먼저 완성되고 화면이 비어 있는** 상태다.

- 라우팅, 라우트 가드, 세션, 온보딩 단계 머신, OpenAPI 기반 API 클라이언트가 모두 동작한다.
- 화면은 사실상 백지다. 예: `src/routes/onboarding/terms.tsx` 는 `<div>약관 동의</div>` 10줄이다.
- 공통 컴포넌트는 shadcn 기본 5종(`button`, `field`, `input`, `label`, `separator`)뿐이고, 디자인과 무관한 무채색 상태다.

반면 디자인은 이미 전부 끝나 있다. 피그마 `취얼스` 페이지(`233:153`)에 8개 섹션, 약 30개 화면이 **Desktop 1440 / Mobile 393 두 벌로** 그려져 있고, 별도의 `00 · 디자인 시스템` 섹션에 토큰과 컴포넌트가 상태별로 정의돼 있다.

**이 작업은 한 사람이 혼자 한다.** 따라서 가장 큰 비용은 구현 난이도가 아니라 *되돌아가는 일*이다. 공통 층을 나중에 바꾸면 그 위에 쌓은 화면을 전부 다시 만져야 하고, 혼자서는 그걸 흡수할 여력이 없다. 이 문서의 핵심은 기능 목록이 아니라 **순서**다.

## 2. 목표

1. 나중에 바뀌면 모든 화면이 흔들리는 층(토큰, 폰트, 전역 CSS, 레이아웃 셸, 브레이크포인트)을 **화면 작업 전에 고정한다.**
2. "학생이 가입해서 선배에게 커피챗을 신청하고 결과를 확인한다"는 **한 줄기를 끝까지 동작하게** 만든다. 모바일과 데스크톱 양쪽에서.
3. 공통 컴포넌트는 미리 만들지 않고, 줄기를 구현하다 **두 번째로 같은 것이 필요해지는 순간** 승격시킨다.

성공의 모습: 토큰 층을 건드리지 않고도 남은 20화면(선배 가입, 선배 계정, 받은 신청)을 같은 패턴의 반복으로 채울 수 있는 상태.

## 3. 비목표

이 문서가 다루는 범위가 **아닌** 것. 하지 말라는 뜻이 아니라, 이 작업 묶음 안에서 하지 않는다는 뜻이다.

- 피그마 30화면 전체 구현. 이 범위는 **토큰 층 + 학생 줄기 11화면**이다.
- 섹션 `03 · 선배 가입·인증`, `06 · 선배 계정·받은 신청`, `08 · 사원증 디자인`.
- 다크 모드.
- 태블릿 전용 레이아웃.
- `00 · 디자인 시스템` 섹션에 그려진 컴포넌트 15종의 선행 구현.
- API 연동 변경. 로직은 이미 서 있으므로 화면을 거기에 붙이는 것이지, 로직을 고치는 작업이 아니다.

## 4. 안티골 — 기술적으로 완성돼도 실패인 것

- **컴포넌트는 다 있는데 돌아가는 화면이 하나도 없는 상태.** 디자인 시스템을 선행 구현할 때 흔히 빠지는 결말이고, 이 설계가 피하려는 주된 실패다.
- **데스크톱만 되고 모바일이 깨진 화면이 쌓이는 것.** 한 화면의 두 폭은 같은 커밋에서 끝낸다. "나중에 모바일 대응"은 되돌아가는 일을 미래에 쌓아두는 것이다.
- **피그마 수치를 그대로 하드코딩하는 것.** `padding: 24px` 가 아니라 토큰을 쓴다. 토큰을 깔고도 안 쓰면 토큰을 깐 의미가 없다.
- **공통 컴포넌트를 한 번 쓰고 추상화하는 것.** 두 번째 사용처가 나타나기 전에는 화면 안에 둔다.

## 5. 제약

### 5.1 기술 스택 (기존재, 변경하지 않음)

React 19 / TypeScript / Vite 8 / Tailwind CSS v4 / TanStack Router / TanStack Query / `@base-ui/react` / shadcn / react-hook-form + zod / zustand.

Tailwind v4이므로 토큰은 `@theme` 에 선언하면 유틸리티가 자동 생성된다. 피그마 변수명이 이미 `--cheers-*` 꼴이라 거의 그대로 옮길 수 있다.

### 5.2 디자인 제약

- **폭은 두 개뿐이다**: 393(Mobile), 1440(Desktop). 중간 폭 시안은 존재하지 않는다.
- **폰트는 Noto Sans KR.** 현재 코드에는 Inter가 들어와 있다.
- **타이포 토큰이 폭마다 분리돼 있다.** `Cheers / Task/Title desktop`(40/56/-1.4)과 `Cheers / Task/Title mobile`(32/44/-1.0)이 별개 스타일이다. 즉 브레이크포인트에서 바뀌는 것은 레이아웃만이 아니라 토큰 값이다.
- **라이트 고정.** 다크 시안이 없으므로 OS 설정과 무관하게 항상 라이트로 렌더한다.

### 5.3 제품 규칙 (피그마 `구현·정책 메모`, 노드 `344:9344`)

디자인 취향이 아니라 명시된 규칙이므로 임의로 바꾸지 않는다.

- **상세 열람**: 로그인 상태에서 신청 상세는 PC에서 목록 위 **모달**, 모바일에서 **전체 화면**으로 연다. 로그아웃 상태면 로그인 후 동일한 신청으로 복귀한다.
- **스크롤**: 모바일의 긴 상세·입력 화면은 본문 스크롤을 지원한다. PC 모달은 본문만 스크롤하고 닫기 버튼과 주요 버튼은 항상 접근 가능하게 유지한다.
- 권한 확인 전에는 학생 정보를 표시하지 않는다.
- 연락처 공유 자체는 커피챗 수락·일정 확정이 아니다. UI가 그렇게 읽히면 안 된다.
- 현재 UI에 읽음·거절·만료·취소 기능은 **의도적으로 없다.** 임의로 추가하지 않는다.
- 피그마의 회사 로고, 닉네임, 질문, 연락처, 명함은 **예시 데이터**다. 실제 자산이 아니다.
- 소셜 로그인은 Google만 활성화한다. 카카오·네이버는 비활성 상태로 표시한다.

### 5.4 현재 코드의 걸림돌

`src/index.css` 는 Vite 스타터 템플릿 잔재를 그대로 안고 있다. 토큰 작업 전에 치워야 한다.

- `#root { width: 1126px; text-align: center; border-inline: 1px solid var(--border); }` — 모든 화면을 1126px 박스에 가두고 전체를 가운데 정렬한다. 반응형의 첫 번째 장애물.
- 보라색 accent 변수, `#social .button-icon` 같은 템플릿 잔여물, `h1`/`h2`/`code` 전역 스타일.
- shadcn 기본 무채색 oklch 토큰 한 벌 — Cheers 색과 충돌한다.
- `@media (prefers-color-scheme: dark)` 블록과 `.dark` 클래스 토큰.
- `--font-sans: 'Inter Variable'`.

## 6. 결정된 사항

### 6.1 사용자가 정한 것

1. **디자인 시스템을 둘로 쪼갠다.** 토큰·전역 CSS·레이아웃 셸은 선행 구현하고, 개별 컴포넌트는 줄기를 구현하는 과정에서 필요할 때 만든다.
2. **한 줄기를 먼저 끝까지 뚫는다.** 섹션 순서대로 30화면을 채우지 않는다.
3. **다크 모드는 끄고 라이트로 고정한다.**
4. **혼자 구현한다.**

### 6.2 설계 과정에서 내가 정한 것 (사용자 확인 전, 빌더가 뒤집어도 되는 것)

- **브레이크포인트는 하나.** Tailwind 기본 `lg`(1024px)를 경계로 쓴다. 미만은 393 시안의 레이아웃, 이상은 1440 시안의 레이아웃. 기존 `index.css` 도 이미 `max-width: 1024px` 를 쓰고 있어 일관된다.
- **태블릿은 데스크톱 쪽에 붙인다.** 중간 시안이 없으므로 전용 레이아웃을 만들지 않는다.
- **모바일 퍼스트로 작성한다.** Tailwind의 기본 방향이고, 기본 스타일에 모바일을 두고 `lg:` 로 데스크톱을 덧씌우면 분기가 한 방향으로만 생긴다.
- **한 줄기의 범위**는 아래 7.4~7.5에 적은 11화면으로 본다.

## 7. 구현 순서

각 단계는 **그 단계가 끝나면 눈으로 확인할 수 있는 상태**로 끝나야 한다.

### 단계 0 — 바닥 치우기

`src/index.css` 에서 5.4에 나열한 스타터 잔재를 제거한다. 다크 블록과 `.dark` 토큰, Inter 폰트, `#root` 고정폭도 여기서 같이 걷어낸다. 화면이 일시적으로 못생겨지는 건 정상이다.

끝난 상태: 기존 라우트가 아무 스타일 없이 왼쪽 정렬로 뜬다. 1126px 박스가 사라져 있다.

### 단계 1 — 토큰 층

피그마 변수를 Tailwind v4 `@theme` 으로 옮긴다. 색(`--cheers-v05-*`, 브랜드), 간격(4/8/12/16/20/24/32/40/48/64), radius(4/8/12/full), border width, 그림자(`Elevation/Work surface`), 타이포 스케일 전부.

폭마다 값이 다른 타이포(`Task/Title`)는 **토큰 하나에 반응형을 심어** 호출부가 분기를 모르게 한다. 호출부마다 `text-[32px] lg:text-[40px]` 를 쓰면 11화면에 흩어지고 나중에 바꿀 수 없다.

Noto Sans KR을 올린다. 한글 가변 폰트는 용량이 크므로 서브셋과 로딩 전략을 여기서 정한다.

라이트 고정은 `<html>` 레벨에서 `color-scheme: light` 를 못박는 방식으로 한다.

끝난 상태: 토큰 이름만으로 피그마 색·간격·타이포를 꺼내 쓸 수 있다. 다크 설정 기기에서도 라이트로 뜬다.

### 단계 2 — 레이아웃 셸

`Cheers / Header`(`353:9429`)와 `Cheers / Footer`(`353:9657`)를 구현하고 `__root.tsx` / `_app.tsx` 에 붙인다. 페이지 컨테이너(최대폭, 좌우 여백, 모바일/데스크톱 전환)도 여기서 한 번만 정의한다.

이 셸이 **반응형의 본체**다. 개별 컴포넌트는 폭이 유동적이면 그만이고, 실제로 깨지는 건 레이아웃 층이다.

끝난 상태: 빈 라우트에서도 헤더·푸터·여백이 두 폭 모두 시안과 맞는다.

### 단계 3 — 줄기 전반 (가입)

순서대로, 각 화면마다 두 폭을 같은 커밋에서 끝낸다.

1. 랜딩 (`352:9464` / `352:9465`) — 히어로 2열↔1열, 선배 카드 4열↔2×2
2. 학생 로그인 (`334:5733` / `334:5643`)
3. 약관 동의 (`334:6123` / `334:6011`) + 동의 완료 상태 + 약관 모달 2종
4. 학교 이메일 인증 (`334:6585` / `334:6495`)
5. 인증번호 입력 (`334:6781` / `334:6675`) + 만료 + 불일치 상태
6. 학생 기본 정보 (`335:6814` / `335:6675`)
7. 학생 추가 정보 (`335:7095` / `335:6954`)

**스텝 인디케이터 주의.** 피그마에 `Signup progress / Desktop`(좌측 세로 리스트)과 `Signup progress / Mobile`(상단 가로 탭)이 **별도 컴포넌트로** 그려져 있다. 단순 reflow가 아니다. 다만 데이터는 하나이고, `src/routes/onboarding.tsx` 가 이미 `step` 을 라우트 컨텍스트로 내려주므로 그 값을 받아 그리기만 하면 된다. 새 상태 관리를 만들지 않는다.

**약관 모달도 형태가 바뀐다.** 데스크톱은 중앙 다이얼로그, 모바일은 전체 화면이다. 5.3의 상세 열람 규칙과 같은 패턴이므로, 여기서 만드는 것은 일회성 모달이 아니라 **줄기 후반에서 재사용할 반응형 오버레이**다. 이 하나만은 두 번째 사용처가 보이므로 처음부터 공통으로 만들어도 좋다.

### 단계 4 — 줄기 후반 (탐색·신청)

8. 선배 둘러보기 · 학생 (`352:9466` / `352:9467`)
9. 커피챗 신청 (`336:7965` / `336:7879`)
10. 커피챗 신청 완료 (`337:7304` / `337:7217`)
11. 보낸 신청 (`337:7514` / `337:7389`) + 상세 (`337:7717` / `337:7637`) + 없음 (`337:8004` / `337:7920`)

상세는 5.3 규칙대로 PC 모달 / 모바일 전체 화면이다. 단계 3에서 만든 오버레이를 여기서 쓴다.

### 단계 5 — 회수

줄기를 다 뚫은 뒤, 화면 안에 흩어진 것 중 **두 번 이상 쓰인 것만** `src/components/ui` 로 올린다. 실제 데이터에 한 번 물려본 뒤라 모양이 맞는지 알고 하는 추출이 된다.

이 시점에서 Field·Button·Checkbox·Choice·Social·Signup progress·오버레이가 자연스럽게 모일 것으로 본다. 그 뒤 선배 가입(03)과 선배 계정(06)은 같은 패턴의 반복이라 훨씬 빠르게 채워진다.

## 8. 빌더에게 맡기는 것

- 토큰 이름 규칙. 피그마 변수명을 그대로 쓸지(`--cheers-v05-text-primary`), Tailwind 관례로 다듬을지(`--color-text-primary`).
- Noto Sans KR 로딩 방식 — `@fontsource`, 서브셋 범위, `font-display`.
- 반응형 타이포 토큰을 CSS 커스텀 프로퍼티 + 미디어 쿼리로 할지, Tailwind 유틸 조합으로 할지.
- 반응형 오버레이를 `@base-ui/react` Dialog 하나로 두 모드를 내게 할지, 폭에 따라 다른 컴포넌트를 렌더할지.
- 기존 shadcn 컴포넌트 5종을 토큰에 맞춰 고칠지, 새로 만들지.
- 각 화면의 로딩·에러 처리 수준. 피그마에 `불러오는 중` 시안이 약관 화면에만 있다.
- 커밋 단위와 브랜치 전략.
